# 面试问答总结：数据库选型、SQLite、连接与 bcrypt

## 1. 主流关系型数据库的选型

### 问题
主流关系型数据库怎么选？

### 答案
数据库选型不是看“谁更流行”，而是看项目场景：
- `SQLite` 适合单机、轻量、低并发、易部署场景
- `MySQL` 适合标准业务 CRUD、生态成熟、团队熟悉度高的场景
- `PostgreSQL` 适合复杂查询、强约束、JSON/扩展能力更强的场景

### 面试口语版
> 我选数据库主要看业务形态和运维成本，不是看品牌偏好。这个项目如果是轻量、单机、低并发，就更适合 SQLite；如果是标准业务系统、并发更高、团队对 MySQL 更熟，MySQL 也完全可以；如果需求更复杂、SQL 表达力和扩展性要求更高，我会优先考虑 PostgreSQL。

---

## 2. 为什么不选 MySQL 而选择 SQLite

### 问题
如果面试被问到“为什么不选 MySQL，而选 SQLite”，该怎么回答？

### 答案
核心逻辑是：**这个项目不是典型的中心化高并发数据库系统，而是轻量、文件化、以 Git / Markdown 为主的工作流系统**。数据库更多承担的是索引、状态和结构化解释层，而不是所有事实的唯一来源。

所以不选 MySQL 的原因通常是：
- 引入 MySQL 需要额外的服务部署和运维
- 当前业务量和并发不一定需要 MySQL 的能力
- SQLite 更轻量，和本地文件、单机部署更贴合
- 项目的单一事实源在 Git / Markdown，不想让数据库成为另一套主存

### 面试口语版
> 这个项目的核心事实其实在 Git 里的 Markdown，数据库只是做索引和结构化辅助，所以我没选 MySQL。MySQL 当然很强，但对于这种轻量、低并发、强调单机部署和快速交付的场景，引入一个重型数据库服务的收益不够大，反而会增加部署和维护成本。SQLite 更符合这个阶段的需求。

---

## 3. 为什么 SQLite 里“像 ORM 那样长期持有一个 session”并不总是最优

### 问题
这句话怎么解释？

### 答案
SQLite 是文件型数据库，不是服务型数据库。长期持有一个 `session` 或 `connection` 不一定带来收益，反而可能：
- 长时间占用锁
- 增加 `database is locked` 的概率
- 让状态管理更复杂
- 带来旧数据、缓存一致性等问题

SQLite 更适合短连接、短事务、用完即关的模式。

### 面试口语版
> SQLite 更偏向短连接和短事务模式。长期持有 session 不一定更快，反而容易带来锁竞争和状态复杂度，所以在这个场景里我更倾向于方法级打开、用完即关的方式。

---

## 4. 连续一段时间内同时向 SQLite 发起 connect 会怎么处理

### 问题
如果一段时间内同时向 SQLite 发起很多 `connect()`，会怎样？

### 答案
SQLite 的关键限制不是“连不上”，而是**文件锁**：
- 多个连接通常都能建立
- 多个读一般问题不大
- 写操作会被串行化
- 读写冲突时可能等待
- 写太密集时可能报 `database is locked`

所以并发连接多的时候，真正的瓶颈是写锁，而不是 `connect()` 本身。

### 面试口语版
> SQLite 允许很多连接同时建立，但它本质是文件锁模型，不是服务型数据库。并发读通常问题不大，但写操作会被串行化；如果写太密集，就可能出现锁等待或者 `database is locked`。所以它更适合低并发、短事务场景。

## 5. SQLite 连接模式怎么理解

### 问题
`server/pivot_users.py` 这种写法是不是每一次查询都要走 `_db.connect()`？

### 答案
是的，当前代码基本是**方法级短连接**：
- 每个 repo 方法调用时打开一个连接
- 方法结束后关闭连接
- 一个方法内部如果又调用别的方法，可能会再次打开连接

例如 `create()` 里写完后再 `get()`，就会多一次连接。

这种方式的优点是：
- 简单清晰
- 连接生命周期短
- 更适合 SQLite 的短事务模型

### 面试口语版
> 当前仓储层是方法级短连接设计，每个方法自己打开和关闭 SQLite 连接。这样实现简单，也更符合 SQLite 的使用方式。对于现在的规模这是足够的，如果后面发现重复连接成本变高，我会再把同一业务链路合并到一个连接或事务里。

## 6. SQLite 并发写入时的处理方式

### 问题
如果连续一段时间同时向 SQLite 写数据，会怎么处理？

### 答案
SQLite 通过**文件锁**来保证一致性：
- 写入时需要获得更强的锁
- 其他写请求会等待
- 如果等待太久，可能超时或报错
- 可以通过 `busy_timeout` 让它先等待一会儿

### 面试口语版
> SQLite 的并发瓶颈主要在写入。它会通过文件锁来保证一致性，写操作基本是串行的。如果写得太密集，就可能出现锁等待或者超时，所以它适合低并发、短写入的场景。

## 7. bcrypt 是什么

### 问题
`bcrypt` 是啥？

### 答案
`bcrypt` 是一种**密码哈希算法**，不是传统意义上的加密。它的作用是：
- 安全存储密码
- 验证密码
- 抵抗暴力破解

它的特点是：
- 自带盐值（salt）
- 计算故意较慢
- 可以调节成本因子（cost factor）

### 面试口语版
> bcrypt 不是加密，而是密码哈希。它的特点是自带 salt，而且计算成本可调，故意算得慢，这样即使数据库泄露了，攻击者也不容易快速暴力破解密码。

## 8. 结合 Pivot 产品设计，为什么项目更偏向 SQLite

### 问题
结合 `pivot-product.md`，为什么项目更适合 SQLite？

### 答案
Pivot 的核心设计是：
- `matter` 是顶层事项
- 原始事实在 Git / Markdown 里
- 数据库主要是索引、状态和解释层
- 系统强调单一事实源，不希望 Git 和 SQL 双主存并存

因此 SQLite 更适合当前阶段，因为它：
- 轻量
- 单文件
- 易部署
- 更贴合本地工作流
- 适合作为辅助索引层，而不是主存层

### 面试口语版
> Pivot 的核心事实不在数据库里，而在 Git 里的 Markdown。数据库只负责索引和状态解释，所以我没选 MySQL 这种更重的方案，而是选了 SQLite。这样更轻量，也更符合单一事实源的设计，不会让 Git 和 SQL 形成双主存。

## 9. 一段更完整的数据库选型面试回答

> 我做数据库选型时主要看三个维度：业务形态、并发特征和运维成本。像 Pivot 这种以 Git / Markdown 为事实源、数据库只做索引和状态层的系统，SQLite 更轻量，也更符合单机、低并发、快速交付的目标。MySQL 当然不是不好，但它更适合中心化、标准业务 CRUD 和服务化部署的场景；如果以后并发和协作规模明显上升，我也会考虑迁移到 MySQL 或 PostgreSQL。

---

## 10. 一段更短的“背诵版”

> 这个项目的核心事实在 Git / Markdown，数据库只是辅助索引和状态层，所以我没有选 MySQL，而是选了更轻量的 SQLite。SQLite 部署简单、和单机文件工作流更贴合，也更符合当前低并发、快速交付的需求。

---

## 11. 面试回答时的表达原则

- 不要说“MySQL 不如 SQLite”
- 不要说“SQLite 永远比 MySQL 更好”
- 要说“**场景更匹配**”
- 要强调“**不是数据库强弱，而是系统需求**”
- 要强调“**现在的选择，不代表未来不能迁移**”

---

## 12. 可直接背诵的结论

> 选型不是看谁更强，而是看谁更适合这个系统。这个项目里，Git / Markdown 才是事实源，数据库只负责索引和状态解释，所以我选了 SQLite 来降低部署和运维复杂度。MySQL 当然可以做，但在这个阶段收益不够大；如果未来并发和查询复杂度上来了，再迁移也很自然。
